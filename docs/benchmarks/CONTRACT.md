# Future Thiran benchmark claim contract

No benchmark result or speed target is established by TH-003. A benchmark manifest is metadata completeness, not measurement evidence. Claims require a repeatable method and an independently checked quality/correctness condition before speed is interpreted. See `docs/language/CONSTITUTION.md` and TH-LD-022.

Every future claim must record: benchmark ID; exact git revision; compiler version/build; workload; model and weight identity when relevant; quality/correctness condition; CPU/GPU model; driver/runtime; precision/numeric profile; batch; shapes; context/state size; warm/cold status; AOT/JIT state; cache state; memory-allocation policy; host/device transfer boundary; synchronization point; warmup count; measured iteration count; raw samples; median, p95, and p99; peak memory where measurable; and failure count. Units, timer/measurement method, sample selection, and environment controls belong in the workload or method record. Legitimately unavailable values are `null` and must be explicitly described before publication; unknown is not a measured zero.

Category is one of `KERNEL`, `MODEL_PREFILL`, `MODEL_STEP`, `END_TO_END_REQUEST`, or `RENDER_FRAME`. A kernel timing cannot be presented as model speed. Prefill and stateful step are distinct; an end-to-end request includes declared transfer, synchronization, application, and response boundaries; rendering claims use frame boundaries. Separate categories need separate IDs and samples.

`tests/spec/benchmark_manifest_example.json` is intentionally all-null and unmeasured except for its illustrative ID/category. `python3 -B tools/benchmark_manifest.py tests/spec/benchmark_manifest_example.json` checks that every mandatory field is present, category is recognized, and any provided sample count matches measured iterations. It does not attest hardware, correctness, timing, quantiles, or publication readiness. Never replace missing measurements with aspirations.
