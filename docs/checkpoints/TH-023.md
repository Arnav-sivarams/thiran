## 3. Frozen benchmark methodology

- Inputs: deterministic rank-1 `f32`; `x[i]=f32(((i*17)%1009)-504)/f32(37)`
  and `y[i]=f32(((i*29+11)%1013)-506)/f32(41)`.
- Sizes: small 1,024, medium 1,048,576, large 16,777,216 elements.
- Elementwise chain: add, negate, multiply, subtract, multiply. Thiran fused
  `{reuse=true,fusion=true}` versus unfused `{false,false}`; competent C++20
  one-loop fused and five-vector/five-loop materialized baselines.
- Extension: medium `-x -> research_square_linear(a) -> +y` versus the exact
  built-in `a*a+a` representation.
- Materialization: medium multiple-consumer chain in which `a=x+y` feeds two
  consumers and must materialize.
- Process fixture: two positive deterministic 32-element literals and the
  accepted standalone add/multiply/subtract/add chain.
- TH-017: accepted 200-step affine reference model, checkpoint/reload/snapshot,
  input `[2.0]`; deployment overhead only.
- Warm in-process CPU: 5 warmups, 30 samples, one invocation. GPU: 10 warmups,
  30 samples, one invocation. C++ batches: 8,192/8/1. Framework batches:
  256/8/1. Build/source/artifact/model processes: 10 independent samples.
- CPU comparison order rotates left by round across Thiran fused, C++ fused,
  Thiran unfused, C++ materialized. GPU and extension pairs use A/B/B/A.
- CPU microbenchmarks and frameworks are pinned with `taskset -c 8`; builds and
  GPU process measurements are unpinned.
- GPU wall time starts immediately before production execution and ends only
  after `observe()`/`cuEventSynchronize`; it includes H2D, module load/Driver
  JIT, allocation, launch, execution, D2H, and publication. Qualified
  kernel-only timing is unavailable.
- Every implementation is checked bitwise against the scalar `f32` reference
  before timing, and deterministic FNV-1a output digests are checked after
  timed calls. Statistics are median, mean, population standard deviation,
  interpolated p10/p90, minimum, and maximum. Median is principal.

The surviving methodology was already frozen before measurements. It remains
authoritative.

## 8. TH-015 fusion analysis

`SUPPORTED` structurally: fusion changed five groups, five loops/kernels, five
materialized intermediates, seven slots, and `20*N` temporary bytes into one
fused group, one loop/kernel, one materialized result, three slots, and `4*N`
temporary bytes. On GPU it also reduced planner allocations 5→1 and requested
allocation bytes `28*N`→`12*N`.

`SUPPORTED` for this CPU chain: fused timing improved by 20.9–23.5%, with
separated p10–p90 bands at all sizes. `INCONCLUSIVE` on GPU timing: median
improvements were only 0.24%, 1.07%, and 0.59%, with strongly overlapping
distributions. Structural reduction does not imply a measurable end-to-end GPU
gain under the current transfer/module-load boundary.

## 9. TH-021 extension performance

At medium size, CPU generic extension was 460.812 ms median versus 493.521 ms
for the built-in representation; GPU was 354.549 versus 363.125 ms. The generic
path formed one fused group/kernel and one materialized intermediate; the
built-in representation formed two groups/kernels and two materialized
intermediates. Generated C++/PTX audits found direct scalar recipe operations
and no registry lookup, dynamic loading, evaluator call, callback, or symbolic
extension dispatch in the hot loop. Runtime lookup/callback counters were zero.

`SUPPORTED`: generic extension machinery leaves no runtime registry/callback
dispatch in the hot loop. `SUPPORTED` for this CPU chain: no positive extension
overhead was observed; it was 1.071x faster by median with non-overlapping
p10–p90 bands because its declared recipe enabled the one-group structure.
`INCONCLUSIVE` on GPU timing because distributions overlap. This is not a broad
claim that extensions are faster.

## 10. Materialization / memory analysis

The legitimate medium multiple-consumer workload produced three groups, three
loops/kernels, three materialized intermediates, five slots, two reusable
temporary slots, and 12,582,912 logical temporary bytes. GPU used five
allocations requesting 20,971,520 bytes, two H2D copies/8,388,608 bytes, one
D2H copy/4,194,304 bytes, three launches, one module/Driver-JIT load, and one
synchronization. Median time was 520.718 ms CPU and 358.790 ms GPU.

`SUPPORTED` structurally: the multiple-consumer value prevents full fusion and
materializes. `NOT COMPARABLE`: its timing is not divided by the linear chain
because the mathematics differ.

## 15. External baseline fairness audit

- Same deterministic `f32` inputs, operation order, output materialization,
  bitwise correctness obligation, digest consumption, CPU affinity, and
  single-thread policy were enforced.
- C++ used GCC 13.3 with exact documented `-O3`, `-DNDEBUG`, no fast-math, and
  disabled contraction. No OpenMP, native-ISA flag, volatile handicap, dead
  output, or deliberately weak loop was used.
- Thiran used production JIT/artifact flags, ABI copies, allocation, and current
  scalar backend behavior. The comparison therefore measures the system, not
  pure loop code generation.
- NumPy used vectorized eager `float32`; PyTorch used eager tensor expressions,
  one CPU thread, and synchronized CUDA. CUDA resident and inclusive scopes are
  separate.
- A broad “Thiran vs C++” conclusion is not drawn from this one chain.

## 16. Key findings

- `SUPPORTED`: the benchmark and recovery evidence are complete, deterministic,
  synchronized, and auditable.
- `SUPPORTED`: TH-015 fusion reduces five groups/kernels and five materialized
  results to one, with materially lower allocation/temporary structure.
- `SUPPORTED`: fusion improves this CPU chain by about 21–24% by median.
- `INCONCLUSIVE`: fusion improves end-to-end GPU time; the bands overlap.
- `SUPPORTED`: Thiran's current CPU execution is much slower than competent
  optimized C++20, NumPy, and single-thread PyTorch for this chain.
- `SUPPORTED`: Thiran transfer-inclusive GPU execution is much slower than the
  installed PyTorch inclusive path in this environment.
- `NOT COMPARABLE`: PyTorch device-resident rows versus transfer-inclusive
  Thiran rows.
- `SUPPORTED`: TH-021 extension lowering has no hot-loop registry/callback
  dispatch.
- `SUPPORTED`: CPU source-run/build latency is dominated by external compilation.
- `SUPPORTED`: current GPU execution repeatedly loads/Driver-JITs a module and
  transfers inputs/results at every call.
- `UNAVAILABLE`: qualified Thiran kernel-only time and CUDA C++/`nvcc` baseline.

## 17. Bottlenecks / performance debt

The evidence identifies: scalar/non-vectorized CPU generated execution plus
per-call ABI/allocation overhead; external compiler cost in CPU build/source
run; per-call GPU context/module/Driver-JIT/allocation and host-device transfer;
lack of persistent device tensors/residency; materialization traffic for
multiple consumers; and absent kernel-only event instrumentation. These are
recorded debt only. TH-023 implements none of vectorization, threading,
persistent tensors, allocator redesign, new fusion, autotuning, or CLI redesign.
