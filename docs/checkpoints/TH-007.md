## Concrete design and contracts

`ResourceId` is a TH-006 compiler safety-resource identity; `StorageObjectId` is a deterministic allocation-object identity; an address is an unobservable implementation detail. `ResourceId != StorageObjectId`, and neither ID is a pointer. A later verified planner may reuse physical storage across non-overlapping logical resources. The first bridge binds a singleton Fresh resource once to a distinct object, resolves AliasOf/ReadViewOf to that object, and binds a proven `IndependentCopyOf` to a deep-copied new object. Unknown/stale IDs, duplicate binding, mismatched copy-source provenance, and fresh-ID storage collision are rejected. Scalar/no-resource facts allocate no tensor storage.

The storage object owns byte memory and reports byte length through `StorageHandle`. The handle currently retains it via an internal standard-library shared lifetime object; `std::shared_ptr` is not a source-language rule. Reference count != borrow checking. Shared storage handle != source alias permission. The object's deterministic ID is assigned by construction sequence, never an address. A Tensor descriptor holds dtype, concrete shape, positive element strides, element offset, handle, and materialized/view plus debug contiguity classification. Rank derives from shape length. Logical i64 reads/writes use checked offsets and `memcpy` on byte storage, avoiding unproven alignment/aliasing casts and unchecked pointer arithmetic.

The bridge snapshots the created-resource facts it needs, so a C++ analysis-result wrapper can expire without leaving a dangling reference in the adapter.

| Dtype | Byte width | Current execution |
| --- | ---: | --- |
| bool | 1 | descriptor validation |
| i32, u32, f32 | 4 | descriptor validation |
| i64 | 8 | checked values/views/copy/write |
| u64, f64 | 8 | descriptor validation |

Materialized i64 tensors use offset zero, exact byte count, and checked conventional row-major strides. For `[2,3]` strides are `[3,1]`; for `[2,3,4]` they are `[12,4,1]`. Contiguity is logical row-major, not `offset == 0`; a row view with nonzero offset can be contiguous. Zero-sized axes are valid and can use zero-byte storage. An empty descriptor's offset may be at most one-past its allocation in elements, and no empty tensor/view is dereferenced. An empty derived view may canonicalize its arithmetic cursor to that safe one-past offset. Checked numel, stride product, byte count, offset addition/multiplication, and maximum reachable offset reject overflow before allocation or access.

Partial indexing, positive half-open slicing, mixed integer/slice selectors, rank-two transpose, and chained views compose shape/strides/offset while retaining the same storage handle. An ordinary C++ Tensor handle alias corresponding to immutable `let B = A` shares storage without data copy. Explicit `copy` of materialized or strided/transposed i64 input iterates logical row-major elements into independent contiguous storage. `reshapeView` requires equal checked count and contiguous input and does not copy; `reshapeCopy` explicitly materializes i64 data. No hidden COW exists: the low-level test writes the original and observes the write through alias/view, but not through an earlier explicit copy.

`MutableTensorRef` is move-only, retains its descriptor/handle rather than a potentially dangling C++ wrapper reference, and offers checked i64 writes to the existing object. It is infrastructure requiring prior TH-006 exclusivity proof, not an unrestricted safe source mutation API. The future lowering rule is `TH-006 exclusive mutable proof -> TH-007 MutableTensorRef -> concrete write`; shared handle count cannot replace that proof. The test invokes the primitive directly under an assumed legal lowering context; user-visible indexed assignment is not implemented.

StorageHandle retention may keep bytes physically alive after a C++ root object disappears. It does not legalize a Thiran view whose source root moved, whose view escaped, or whose mutation conflicts under TH-006. The unchanged ownership tests enforce those source rules separately. The semantic `ShapeFact` bridge verifies dtype/rank, known extent equality, unknown-slot rank and concrete nonnegative i64 extents before access. Checked standalone utilities return shapes for trailing-axis broadcast (including zero with one and rank-zero scalar), rank-two matmul, and rank-dropping `sum(axis)` including zero-sized reduction axes. No numerical kernel is executed merely because these shape contracts exist.

The independent verifier rejects manually malformed rank/stride, zero-stride, storage-range, reachable-offset, overflow, invalid-dtype, missing-handle, impossible materialized, and false-contiguity descriptors before access. Semantic bridge checks reject runtime rank and known-extent mismatch. Developer observation separates logical dtype/shape/values/classification from debug layout ID/offset/strides; no address, timestamp, or allocator-dependent identity is emitted. These observations are not public artifact schemas.

## Mechanical matrices

`V0StorageTests` exercises ST01–ST36: contiguous rank-1/2 values and deterministic strides; shared ordinary alias, deep copy and logical values; partial/full index, positive and stepped slices, mixed selectors, transpose/chained views, strided-copy contiguity; low-level alias/view-visible mutation without COW and isolated copies; empty construction/views and non-dereference; overflow/bounds/slice errors; nonzero-offset contiguity; broadcast/matmul/sum contracts; distinct ResourceId/StorageObjectId types and conservative bridge; and physical retention versus TH-006 source-lifetime legality. It also exercises `reshapeView`/`reshapeCopy`, dtype byte widths, debug dump repetition, and rejection of forged copy-source provenance. SV01–SV10 manually reject rank/stride mismatch, zero stride, outside element offset, outside reachable element, reachable-offset overflow, invalid dtype, semantic rank mismatch, known extent mismatch, missing view storage, and stale ResourceId. Malformed objects are verified before any load/store.

Iterable-tensor for remains `TH005C-ITERABLE-FOR-DEFERRED`. The existing AST parses it, but structured semantic IR only models If/ForRange/While and TH-006 liveness/root auditing has no iteration-variable view-lifetime region. Enabling it truthfully would require coordinated analyzer, verifier, evaluator, and control-flow ownership work across Break/Continue/Return; the concrete row substrate alone does not justify fabricating a copy or lifetime. This optional feature is not a TH-007 gate.

## Limitations and handoff

TH-007 is host-only, synchronous, and primarily executes i64 tensor values. Other represented scalar dtypes have metadata but no tensor arithmetic/load/copy execution. No numerical addition/matmul/reduction kernel, native code generation, AD, GPU/device storage, asynchronous events, FFI, persistent file format, stable in-memory ABI, general Buffer runtime, returned-view lifetime syntax, sophisticated memory reuse, whole-program storage lowering, AOT/JIT, or production V0 CLI route is claimed. Storage tests are not native-execution equivalence evidence. TH-008 may consume this verified substrate only under a separately authorized checkpoint; TH-008 was not begun here.
